# Introduction

Recording Studio MCP is a Streamable HTTP adapter. It speaks MCP. Domain writes still go through Recording Studio API. Access still goes through Accessible.

Hosts mount live docs with `recording_studio_mcp_docs_for`. That page reads the host catalog for the named API. Built-in tools:

- `list`, `show`, and `describe` for reading
- `read_skill` for the text of a skill this connection can already see. Pass the name from `describe`.
- `create` and `update` for writing. A blank `parent_id` on create uses this connection's workspace when that workspace is an allowed parent. A missing parent lists the allowed parent types and, when the workspace is one of them, its id. When the API catalog entry says `parent` is `server`, that create does not ask for `parent_id` and does not send one.
- `capability_action` for named API capability actions. An optional `idempotency_key`, or the `Idempotency-Key` header, replays an action flagged `creates: true` when the input matches. A different input for that key is an error. Other actions ignore the key. Named create tools and those creating actions accept the same key. `describe` lists them in `repeat_safe`.
- `Recording` at `recording://{id}`. `resources/list` returns these in id order, 100 at a time. Follow `nextCursor` until a page leaves it out. Skill and UI resources are on the first page.

`delete` is also a built-in tool. It only appears when a type on that named API enables destroy. A host that enables destroy advertises it.

Type arguments, docs tags, and resource reads use a short public name. `RecordingStudioPresskits::PressKit` shows as `PressKit`. Gems pick readable tool names, as much as possible in `verb_type` form (`show_press_kit`, `feature_press_kit`, `add_quote_section`). When `verb_type` does not fit, use any readable snake_case name. `RecordingStudioMcp.tool_name` is an optional helper for the `verb_type` form. Only duplicates raise. Named `show` / `update` / `destroy` tools require `id`. Named `index` tools list the same optional list fields as generic `list`. A named registered tool for that type looks like `set_embargo_press_kit`. Callers may send the public name or the registered class name. `resolve_type!` maps both through the public-name catalog. That name is `registration.public_name`. A blank `public_name:` is the class name without its namespace. One named API cannot register two types with the same public name. Tool results use that public name for `type` and `recordable_type`. Nested items such as attachments and locations are managed through the parent type's actions (for example `add_image`), not as their own types. `describe` says that. An unregistered type string stays as the API sent it. An untitled resource name is the public name, a space, and the recording id. Call `describe` for the type paragraph, included tools, skills via read_skill, relationships, allowed parents, writable fields, and (when this server includes `capability_action`) available actions.

JSON HTTP APIs stay on Scalar. This gem's docs page is MCP only.

Initialize reports `tools.listChanged: true`. A live session that has already called `tools/list` or `tools/call` receives `notifications/tools/list_changed` on the next `tools/list` or `tools/call` when the named API, the grant's role, or the catalog generation changes. A tool call does not rebuild the tool list to check. The notice goes out on that process's listen stream. A client that is not listening does not receive it. A deploy drops in-memory sessions, so that notice does not cross a restart. Reconnect after a deploy when the app ignores the notice.

Host apps register extra tools at runtime: endpoints, metrics, widgets, skills. Those show up on the mounted live page for that named API. The sidebar lists each tool tag once. `Overview` is first, then the remaining tags in alphabetical order, then `Other tools`. There is no Core group and no Tools group. Ping and the general tools sit under Overview. The Recording resource is not listed there. The sidebar lists exactly the live tools for that named API (`include_tools` plus `describe`). Named typed tools sit under that type's tag. Capability actions without `register_tool` are not sidebar tools. They appear on `capability_action` and in `describe` only when that server includes `capability_action`. Each type's group intro is that type's `describe` payload: the type paragraph, the tools `describe` lists (included generic tools scoped to that type, named typed tools, and registered endpoints), capability action names when `capability_action` is included (with the creates/idempotency_key line when that action creates), parent rules, and relationships. A type that does not list `delete` in `describe` does not list `delete` on the docs page. A tag is shown only when a tool on that server carries it. Intro text does not keep a tag. The sidebar, the no-JS list, and `x-tagGroups` use that rule. An `x-tagGroups` group whose tags are all hidden is left out. Per-type schema components are not on this page. The Overview is the initialize text for that API, plus one line: a view-only connection gets the same text minus the Make changes part. A view-only connection receives the shorter text.
